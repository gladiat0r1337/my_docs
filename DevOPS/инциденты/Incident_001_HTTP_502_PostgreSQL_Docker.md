# Инцидент #001 — HTTP 502 после деплоя Spring Boot

> [!info] Учебный инцидент
> Это **смоделированный сценарий**, который мы разбирали 15.11.2026. Команды, сообщения логов и адреса — примеры, **не отчёт о фактическом сбое** инфраструктуры стажировки.

## Краткое описание

**Симптом:** после деплоя пользователь получает `502 Bad Gateway` при обращении к приложению через Nginx.

**Схема запроса:**

```text
Клиент → Nginx (:80) → Spring Boot (:8080) → PostgreSQL (:5432)
```

**Выявленные в учебном сценарии причины:**
1. PostgreSQL слушал только `localhost` (`listen_addresses = 'localhost'`) и не принимал подключения на Docker IP.
2. После исправления TCP-доступности обнаружилось несовпадение пароля приложения и фактического пароля роли PostgreSQL: постоянный volume сохранял уже инициализированную БД, а изменение `POSTGRES_PASSWORD` в окружении само по себе не изменило пароль существующей роли.

**Результат:** приложение перезапущено; `/actuator/health` возвращает `200 OK` и `UP`, а согласованный с разработчиком эндпоинт `/api/messages` возвращает ожидаемые данные.

## Ход диагностики

### 1. Уточнение уровня ошибки — Nginx

`502 Bad Gateway` говорит, что прокси/шлюз не получил корректный ответ от upstream. Это **не обязательно неисправность самого Nginx**.

Если Nginx запущен на VM как systemd-служба:

```bash
systemctl status nginx
```

**Наблюдение:** `active (running)`. Перезапускать Nginx наугад не стали: сначала собираем факты.

### 2. Проверка контейнеров приложения

```bash
docker ps -a
```

**Наблюдение:**
- `mailservice-dev-app-1` — `Exited (1)`;
- `mailservice-dev-postgres-1` — `Up`;
- прокси продолжал отвечать на HTTP-запросы.

`Exited (1)` означает, что основной процесс контейнера завершился с ненулевым кодом. `Up` у PostgreSQL **не означает**, что база полностью готова к работе.

### 3. Чтение логов Spring Boot

По имени **контейнера**:

```bash
docker logs --tail 50 mailservice-dev-app-1
```

Если находиться в каталоге Compose-проекта, по имени **сервиса** (`app`):

```bash
docker compose logs --tail 50 app
```

**Фрагмент ошибки:**

```text
HikariPool-1 - Exception during pool initialization
org.postgresql.util.PSQLException:
Connection to postgres:5432 refused
Application run failed
```

**Гипотеза:** приложение падает во время подключения к PostgreSQL. На этом этапе нельзя утверждать, что ошибка именно в пароле, сети или коде.

### 4. Проверка готовности PostgreSQL

```bash
docker exec mailservice-dev-postgres-1 pg_isready
```

**Результат:**

```text
/var/run/postgresql:5432 - accepting connections
```

Эта проверка по умолчанию использовала **локальный Unix-сокет**, а не сетевой путь между контейнерами.

Дополнительно проверили TCP внутри PostgreSQL-контейнера:

```bash
docker exec mailservice-dev-postgres-1 pg_isready -h 127.0.0.1 -p 5432
```

**Результат:** `127.0.0.1:5432 - accepting connections`.

**Вывод:** PostgreSQL принимает локальные подключения. Доступ с Docker-интерфейса ещё не доказан.

### 5. Проверка Docker-сетей

```bash
docker inspect --format '{{range $name, $_ := .NetworkSettings.Networks}}{{$name}} {{end}}' mailservice-dev-app-1

docker inspect --format '{{range $name, $_ := .NetworkSettings.Networks}}{{$name}} {{end}}' mailservice-dev-postgres-1
```

**Результат:** оба контейнера подключены к `mailservice-dev_default`.

**Вывод:** гипотеза о разных Docker-сетях не подтвердилась, но общая сеть ещё не гарантирует успешное TCP-подключение.

### 6. Проверка параметра прослушивания PostgreSQL

В конфигурации обнаружено:

```ini
listen_addresses = 'localhost'
port = 5432
```

`localhost` относится к **самому PostgreSQL-контейнеру**. Поэтому запрос на `postgres:5432`, который резолвится в Docker IP этого контейнера, не попадал на слушающий TCP-сокет PostgreSQL.

**Исправление в учебном сценарии:** настроили PostgreSQL на прослушивание Docker-интерфейса, перезапустили PostgreSQL и убедились, что правило доступа `pg_hba.conf` соответствует предполагаемым клиентам. Например, `listen_addresses = '*'` слушает все интерфейсы, **но само по себе не настраивает авторизацию и не делает доступ безопасным**. Публиковать `5432` на хост для доступа соседнего контейнера не нужно.

Для проверки **именно межконтейнерного TCP-доступа** использовали диагностический контейнер в сети приложения и команду:

```bash
nc -vz postgres 5432
```

**Результат:** TCP-порт доступен.

### 7. Следующая ошибка — аутентификация

После восстановления TCP-доступности Spring Boot выдал уже другую ошибку:

```text
FATAL: password authentication failed for user "mailservice"
```

Это значит, что сервер PostgreSQL отвечает, но отклоняет учётные данные. Проверка через `psql` **отдельно от Spring Boot** с теми же учётными данными воспроизвела ошибку.

**Причина в сценарии:** в `compose.yaml` у приложения и PostgreSQL использовалось `${DB_PASSWORD}`, но изменение переменной `POSTGRES_PASSWORD` после первоначальной инициализации БД **не меняет пароль существующей роли**. Данные и настройки БД сохраняются в постоянном volume.

**Исправление:** после сверки источников секретов и выбора актуального пароля изменили пароль роли PostgreSQL через привилегированную сессию `psql` (например, интерактивной командой `\password mailservice`). Не выводили секрет в логи/историю команд и **не удаляли volume**. Проверка удалённой аутентификации через `psql` стала успешной.

### 8. Восстановление приложения

Из каталога Compose-проекта:

```bash
docker compose up -d app
docker compose logs -f --tail 50 app
```

`--build` не требовался: код и образ приложения не менялись; исправлены настройки БД и её учётные данные.

**Логи:**

```text
HikariPool-1 - Start completed.
Tomcat started on port 8080 (http)
Started MailserviceApplication
```

Это подтверждает запуск, но ещё не доказывает доступность приложения пользователю.

### 9. Проверка HTTP через Nginx

```bash
curl -i http://192.168.1.100/
```

**Результат:** `404 Not Found`.

Это может быть **нормально**: у Spring Boot не обязательно есть маршрут `GET /`. Заголовок `Server: nginx` не доказывает, что сам Nginx создал 404 — он мог передать ответ приложения.

Проверили реально существующий эндпоинт:

```bash
curl -i http://192.168.1.100/actuator/health
```

**Результат:**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"status":"UP"}
```

И провели простой **smoke test** основной функции:

```bash
curl -i http://192.168.1.100/api/messages
```

Получен `200 OK`, корректный JSON и ожидаемые сообщения; соответствие данных подтвердил разработчик. Таким образом, проверена не только техническая доступность, но и один важный пользовательский сценарий.

> [!note] Про 404 на `/`
> Не нужно автоматически перенаправлять `/` на `/actuator/health` только ради отсутствия ошибки в браузере: для API отсутствие маршрута `/` допустимо. Поведение маршрутов определяется требованиями.

## Что закрепил

| Проверка | Что подтверждает | Чего **не** подтверждает |
|---|---|---|
| `ping` | ICMP-доступность узла | Работоспособность HTTP или TCP-порта |
| `docker ps -a` | Состояние процессов контейнеров | Готовность приложения |
| `docker logs` | Сообщения процесса | Само по себе не доказывает доступность |
| `pg_isready` без `-h` | Локальную готовность PostgreSQL по умолчанию | Межконтейнерный TCP и корректный пароль |
| `nc -vz postgres 5432` | Доступность TCP-порта из точки проверки | Успешную авторизацию в PostgreSQL |
| `psql` с реальными учётными данными | Подключение и аутентификацию (и SQL, если выполнить запрос) | Корректность Spring Boot |
| `curl -i /actuator/health` | HTTP-ответ и результат настроенных health-проверок | Корректность всех бизнес-функций |
| `curl -i /api/messages` | HTTP-ответ бизнес-эндпоинта | Корректность данных без сравнения с ожидаемыми |

## Чек-лист диагностики 502

- [ ] Определить, где возвращается 502, и какой upstream у Nginx.
- [ ] Проверить статус контейнеров: `docker ps -a`.
- [ ] Посмотреть логи приложения: `docker logs --tail 100 <container>`.
- [ ] Проверить зависимости приложения (БД, Redis и т. д.).
- [ ] Разделять DNS, TCP, аутентификацию и SQL-доступ.
- [ ] Убедиться, что проверяем соединение **из правильной сети/контейнера**.
- [ ] Не перезапускать сервисы и не менять конфиги до сбора фактов.
- [ ] После исправления проверить health endpoint **и бизнес-эндпоинт**.
- [ ] Зафиксировать причину, выполненные изменения и способы предотвращения повтора.

## Что улучшить в инфраструктуре

- Добавить healthchecks и smoke tests после деплоя.
- Настроить алерты на недоступность приложения и неуспешные деплои.
- Согласовать управление секретами и процедуру ротации паролей; не хранить реальные пароли в Git.
- Документировать политику хранения и резервного копирования PostgreSQL volumes.
- Использовать минимально необходимые доступы между контейнерами и не публиковать БД наружу без необходимости.
